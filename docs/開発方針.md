# 開発方針

## ポート

- v3 系の開発サーバーは常に `http://localhost:8181` で起動する。
- `8181` が使用中の場合は、別ポートへ逃がさず、使用中のプロセスを確認して停止してから再起動する。
- OAuth callback も `http://localhost:8181/api/auth/callback/x` で固定する。

## Docker

通常環境:

```bash
docker compose up -d --build
```

検証用の分離環境:

```bash
docker compose -f docker-compose.test.yml up -d --build
```

検証用 Compose は別コンテナ、別イメージ、別 volume を使う。

- container: `x-bookmark-viewer-test`
- image: `x-bookmark-viewer:test`
- volume: `app-test-data`

## 認証導線

- 未認証時は直接 X OAuth に飛ばさず、まず `/auth` へ誘導する。
- `/auth` でアカウント追加、active アカウント切り替え、ブラウザーセッション再連携を行う。
- OAuth 成功/失敗後の戻り先も `/auth` にする。
- ブラウザーセッションの解除と、保存済みXアカウント/tokenの削除は別の操作として扱う。セッション再連携でローカルデータや保存済みtokenを削除しない。

## 認証・Origin検証の設計原則

- APIの認証では「XアカウントがDBに存在すること」だけで許可せず、リクエスト元ブラウザーの有効なアプリセッションを検証する。
- 状態を変更するAPIは、セッション認証に加えて同一Originを検証する。`Origin` とアプリが認識する `request.url` が異なることがあるため、実際のリクエスト `Host` も使ってブラウザーOriginを照合する。無関係なOriginは必ず拒否する。
- `Host` は受信リクエストの値としてのみ使い、`X-Forwarded-Host` など任意の転送ヘッダーを信頼元の設定なしに認証根拠として使わない。リバースプロキシ配下で許可Originを広げる場合は、信頼するプロキシと公開Originを明示して検証する。
- 認証失敗（401）とOrigin検証失敗（403）を区別し、画面にはAPIが返すエラーとHTTP状態を表示する。`AUTH_REQUIRED` 等をすべて「ログイン切れ」と表示して原因を隠さない。
- 認証済みユーザーがactiveアカウントを切り替えるときは、active状態とそのブラウザーセッションのアカウント紐付けを同一DBトランザクションで更新する。
- OAuth callback はstateとPKCE verifierを開始元ブラウザーのCookieに照合してから処理し、完了後にブラウザーセッションを発行する。

### 認証・Origin変更の回帰確認

- 正当な同一Originリクエストと、同じブラウザーOriginが別のHost表記（例: `localhost` と `127.0.0.1`）で届くケースをテストする。
- 外部Originのリクエストが状態変更APIを実行できないことをテストする。
- 未認証時の401、認証済み・Origin不一致時の403を別々に確認する。
- 複数アカウント切替後も、activeアカウントとセッションのアカウントが一致し、続く認証済みAPIが成功することを確認する。
- Docker/リバースプロキシを含む実際のアクセスURLで手動確認する。`localhost`、`127.0.0.1`、ホスト名やHTTPSの違いをコード内だけのモックで済ませない。

## 複数アカウント

- X token は `accounts` にアカウントごとに保存する。
- 取得・同期・解除・Undo の対象は active アカウント。
- 統合ビューは `account_bookmarks` を横断して表示する。
- 同じ tweet id が複数アカウントにある場合、表示は1件にまとめ、由来アカウントをカードに出す。

## 並び順

- 既存DBの並びは勝手に再計算しない。
- 今後の「取得」では、取得した active アカウントのページを統合ビューの上へ積む。
- 既存分は下へ押すだけにして、タグ・メモ・折りたたみ状態には触れない。

## 編集時の注意

- `.env` と SQLite DB はコミットしない。
- token、client secret、DBバックアップ、スクリーンショットの扱いに注意する。
- DB構造変更の前には `npm run db:backup` または SQLite backup API で退避する。
